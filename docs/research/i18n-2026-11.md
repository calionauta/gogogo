# Internationalization: own the seam, rent the depth

Reviewed: 2026-11-08

**Question.** Should UI internationalization come from a library,
from the standard library stack, or from a small owned catalog?
And if a library, which one belongs behind the seam?

**Current state.** The template has no localization.
The shell renders a fixed English language tag, UI strings are
hardcoded in markup, the config has no locale setting, and no
middleware reads request language preference.
The binary already ships the locale parsing and printing
machinery as a transitive dependency, unused directly.

## Criteria

The decision uses the gate in the dependency principles page.
Each criterion below maps to one question a reviewer can answer
from the source.

- **Reuse** — does the binary already do it?
  A grep plus the docs map is the check.
  The reuse answer here is the transitive text package.
- **Own the seam, rent the depth** — would a careful engineer
  accept an owned implementation as correct without reading it?
  Language matching and printing pass that test; CLDR plural
  rules for every language do not.
- **Native floor** — does the choice keep pure Go, one binary,
  no second toolchain, no new runtime library?
- **Cheapest to remove** — do library types leak into handlers
  and markup, or stay inside one small package?
- **Agent-legible** — can the behavior be read in one sitting,
  with Go types in and out and misuse failing loudly?
- **Maintenance** — is there a real bus factor and a release
  history a generated project can rely on?

## Evaluated

**The popular lookup library.** The dominant Go translation
library covers lookup and CLDR plural for hundreds of
languages, with named variables through the standard
template syntax and message files in any format the caller
registers. It is the only candidate with a long, adoptable
history: years of releases, thousands of stars, and a major
site generator in production.

Its gaps are known and documented by its own author: no date
and number formatting, templates parsed at runtime with
loose, untyped data, and a bundle that must not be mutated
while readers run. The command-line extractor is a second
toolchain, so a template that pins floating installs cannot
take it at face value.

None of those gaps needs a handler fix.
Each has a small, owned answer: print numbers and dates
through the text package the binary already ships, keep
template data closed and empty, load the catalog once at
boot, resolve request language in one thin edge step, and
pin any command-line tool through the standard tool
directive instead of installing it floating.

**The ICU library.** The newest interviewee offers ICU
message formatting with plural, select and ordinal, atomic
loading, deterministic fallbacks, and request detection
for the standard HTTP stack. It compiles messages at load
and reports precise errors naming file, locale and key.

It fails the gate on maintenance and scope, not quality.
One maintainer, a handful of stars, no production consumer,
and another parser ported from TypeScript that an agent
must audit cold. It also speaks the standard HTTP stack,
not the router this template ships, so it needs a
translation layer at the edge that the popular library
does not.

**The CLDR data library.** The other long-running family
covers plural rules plus date, number, currency and percent
formatting in one package. That coverage is real, and its
date and number functions fill the exact gap above.

It loses on currency of data and maintainer signal. Its
CLDR data is years older than the leader, its health score
lands in the at-risk band with no commits in the last
year, and the API is one generated package per locale.
That is a heavier binary to carry for a smaller, staler
contract.

**Owned catalog on the text package.** A tiny catalog of
embedded JSON files plus the text package's language
parsing and printing covers the current product: English
and Brazilian Portuguese, simple plurals, localized numbers
and dates. It adds no new direct dependency, no new
toolchain, no new maintainer, and it deletes in minutes.

Its honest limit is CLDR depth. Hundreds of languages with
irregular plural rules are a spec-driven problem an owned
map should not re-derive. The plan therefore treats the
owned catalog as the first phase, not the final answer.

## Decision

**Phase one owns the seam and adds no dependency.
Phase two rents CLDR depth behind the same seam, only
on a concrete trigger.** The interface never changes
between phases, so no feature needs a rewrite.

The trade-off line for the pull request is:

Deps: direct text package pinned to the version already
transitive — rejected ICU library on maintainer signal
and the data library on stale CLDR; cost zero new
transitives, zero native surface, types hidden inside one
package; revisit on the fifth locale or the first
irregular plural rule.

## Plan

### Architecture

The seam is a single internal package with three concerns
and one public surface.

- **Catalog** — embedded JSON files, one per locale,
  loaded once at boot into an immutable in-memory store.
  English is the fallback; a missing key renders English,
  never a raw key.
- **Resolver** — pure function from request to language tag.
  Order is persisted preference, then cookie, then the
  request Accept-Language header, then the configured
  default. It reads; it never writes except through the
  cookie set by an explicit preference change.
- **Format** — localized numbers and dates through the
  text printer, never through template functions.

The public surface is one translator interface with a
handful of methods: lookup by key, lookup with a count,
and formatted number and date helpers. Features call
those methods only. No feature imports the underlying
library or the text package directly.

### Wiring

The resolver runs at the edge, above the router, beside
the security headers. No timeout or compression wrapper
may sit above it, or streaming responses break.

The shell renders its language attribute from the
resolved tag in the request context. A fixed tag would
lie to assistive technology about every non-English page.

Locale preference is stored only in a cookie in phase
one. Persisting it per user in the database is a separate
phase, gated on an actual product requirement.

### Configuration

Three environment settings, documented with the rest:

- **I18N_ENABLED** — master switch, disabled by default
  in the template and enabled once a second locale ships.
- **SUPPORTED_LOCALES** — comma-separated supported tags.
- **DEFAULT_LOCALE** — the fallback tag, English.

### Phases

**Phase one, seam plus parsers.** Build the catalog
loader, the resolver, and the translator interface behind
the flag. Seed the two locales. This phase translates
nothing yet; the binary with the flag off is identical
to today.

**Phase one, reference slice.** Convert the Todo
reference slice and the shell chrome to keys. Prove
streaming rendering, patch responses, and the theme
switch keep working in both locales. Rollback is
deleting the package and its registry entry.

**Phase one, hardening.** Add the coverage test that
every invoked key exists in both locales, the boot test
that requests the reference page in each locale, and the
fail-red test that breaks one key to prove the first test
can actually fail. Record the decision here and in the
decision record, with its revisit trigger.

**Phase two, rented depth.** Replace the simple plural
table with the dominant library's CLDR rules, behind the
same translator interface. The catalog format stays JSON.
The flag, the resolver order, and every call site stay
the same. The library loads once at boot and never
mutates while serving.

### Tests and gates

- **Red, green, prove.** Every guarding test destroys
  itself once by hand: break one key, watch it fail,
  revert, watch it pass. A green test that cannot go red
  is not a guard.
- **Coverage.** A static test walks both catalogs and
  every rendered key. Missing translation fails the build.
- **Request path.** An integration test boots the real
  server on an ephemeral port and asserts the document
  language and a translated title per locale.
- **No periodic fetch.** Locale changes travel through the
  existing signal and navigation paths. No timer, no poll.
- **Docs.** Behavior change updates the configuration and
  the decision record in the same commit, and the docs
  claims gate stays green.

## Removal and rollback

Removing localization means deleting one package, its
embedded files, three configuration settings, and one
registry entry. Markup keeps English fallbacks, so the
binary still renders. The same deletion is the rollback
for any phase, including the rented-depth phase.

## Revisit trigger

Rent the CLDR depth when a fifth locale is requested or
when the first language with irregular plural rules ships.
Until then the owned catalog plus the text package is the
cheapest point on the curve: no new maintainer, no second
toolchain, and nothing a later library choice must undo.
