# notify: a delivery engine, and what the template should take from it

Reviewed: 2026-10-27

**Question.** [notify](https://github.com/danmestas/notify) is a self-hosted
notification and durable-communications engine by the DagNats author. Should the
template adopt it, embed it, or copy its shape?

**Short answer.** Copy the contract, rent the providers. The inbox is ours and
stays local; external services are transport behind a per-channel seam.

## What notify is

An MIT-licensed Go server: workflows of ordered steps (`in_app`, `email`, `push`,
`chat`, `sms`, `stream`, `delay`, `digest`, `throttle`, `http_request`,
`agent_message`), subscribers with per-channel preferences, a durable run per
trigger, an inbox with read state, inbound e-mail, and a console.

It runs on DagNats as a **sidecar it does not spawn**, and its HTTP API under
`/v1` carries a `Notify-Contract` header with an additive-only promise.

## What the template already has

DagNats v0.0.30 is pinned here, and the engine primitives notify builds on are
already available and unused by the reference workflow:
`docs/dagnats.md#capability-table` lists `sleep` (duration, input path, cron with
timezone), `idempotency_key`, `rate_limit`/`keyed_rate_limit`, `map`, and cron
triggers. The onboarding demo exercises none of them.

The gap notify exposes is therefore not "the engine cannot", it is "no slice
shows it".

## Options evaluated

| Option | Owner of the inbox | Delivery | Swap later | Verdict |
|---|---|---|---|---|
| Native slice only | template | local | n/a | best demo, no external providers |
| notify as the engine | notify | notify | coupled | smallest code, worst degrade path |
| **Local-first + provider per channel** | **template** | local or external | per channel, by config | **chosen** |
| Provider registry | template | N providers | yes | deferred: third concrete case |
| Outbox + reconciliation | template | N | yes | rejected: goqite and DagNats are already the durable log |

## Decision

**The inbox is local, always.** Messages, read state and preferences live in the
template's own tables, next to `users`, under the same owner scoping and the same
deletion path. An external provider never owns `in_app`.

**Delivery is a per-channel seam.** One package exposes one method,
`Send(ctx, Message) (Receipt, error)`, plus `Name` for the row's evidence.
`in_app` has exactly one implementation (the local one, written by the feature);
`email`/`sms`/`push` can be local or external. A test refuses an external sender
for `in_app`.

**The seam ships, with two transports.** `DELIVERY_TRANSPORT=smtp` reuses the auth
stack's mailer through a function adapter (no copy of the protocol), and
`DELIVERY_TRANSPORT=notify` triggers an external engine over its documented
`/v1/events/trigger`. `off` is the default and records `skipped/provider` rather
than dropping the message. That is the swap the decision promised, proven by a
fake-server test rather than asserted.

**Two modes, never both.** `DELIVERY_MODE=local` owns inbox and preferences
locally. `DELIVERY_MODE=notify` delegates them and the template keeps only a
proxy. Reconciliation between two inboxes is not a feature; it is the bug.

**Never share the DagNats engine.** notify's bridge auth is one global token
(`DAGNATS_BRIDGE_TOKEN`), its streams and buckets assume ownership, and its
documented pin (v0.0.32 at review time) differs from this repo's v0.0.30. The
integration boundary is HTTP, where the contract is explicit.

**No provider token in the browser.** notify's subscriber session is stateless,
valid for one hour, and has no revocation list. A cookie carrying it would
outlive a sign-out-everywhere, which the security model forbids. The inbox is a
server-side proxy: session check in the handler, subscriber id from the session,
API key server-side only.

## The channel model, and the libraries that agree

A **channel** is the medium a person perceives (`email`, `sms`, `chat`, `push`,
`in_app`); a **provider** is who carries it (`smtp`, `notify`, `telegram`). The
split matters because swapping the provider must not change the feature, the
stored row, or the form — only the transport.

The template names only the channels it creates: `in_app` and `email`. Every
other value is data that a provider may know; gogogo does not keep a catalogue,
an address book, or a per-channel env surface for it. That is the line between
"the app records what it told the user" and "the app became a notification
product".

The survey below (October 2026) shows the same split everywhere, which is why
the template adopted it rather than a provider-flavoured API.

| Library | Model | State | Fit here |
|---|---|---|---|
| [containrrr/shoutrrr](https://github.com/containrrr/shoutrrr) | one URL per service (`telegram://`, `discord://`, `smtp://`), `Send(message, params)` | MIT, ~1.5k stars; last push 2026-03, but the last tagged release is v0.8.0 (2023). Active work moved to the [nicholas-fedor fork](https://shoutrrr.nickfedor.com/) (v0.22.0, 2026-10) | the best candidate to adopt later as one `chat` Sender: a URL scheme maps cleanly onto "this channel, that provider" |
| [nikoksr/notify](https://github.com/nikoksr/notify) | service packages, one per platform | many services, but each brings a vendor SDK; its own README warns against critical use | too heavy for a template, and the dependency tree is the opposite of the repo's stance |
| [gopackx/go-notification](https://github.com/gopackx/go-notification) | 7 channels, 24 drivers, `Via()`/`ToMail()` | zero external SDKs, async + retry; young project | the shape is right; too young to make a template depend on it |
| [thinwrap/notifications-go](https://github.com/thinwrap/notifications-go) | a facade per channel, provider chosen by config type | zero dependencies, compile-time provider selection; young | interesting model (a provider that cannot serve a channel is unrepresentable), not enough mileage yet |
| [scttfrdmn/apprise-go](https://pkg.go.dev/github.com/scttfrdmn/apprise-go) | port of the Python Apprise | 86 services, v0.1.0 (2025) | breadth without a track record |
| [argoproj/notifications-engine](https://github.com/argoproj/notifications-engine) | config-driven triggers/templates | Kubernetes-controller shaped (CRDs) | wrong shape for a single binary |

**Verdict: keep the seam, don't adopt a library yet.** The template needs two
providers, both already written (in-process SMTP, notify). A library that
carries fifteen chat platforms buys dependency surface the template does not
use. When a `chat` channel becomes a real requirement, shoutrrr is the one to
wrap: one `Sender`, one URL per deployment, no change to the gate — and the fork
question (which repo to pin) is a supply-chain decision to record then, not now.

## Costs

- A second store means deletion and retention span two systems in `notify` mode.
- Provider swaps do not migrate history or read state.
- Local digest and notify digest do not share semantics; the local one is a
  reference, not a scheduler product.
- The template carries a reference slice, not a notification product. Providers
  beyond SMTP are deliberately absent.

## Rejected

**Embedding.** Every notify package is under `internal/`, so Go forbids importing
it; notify's command package is a server with its own console, migrations and
SMTP receiver.
The dependency delta (a second SQLite driver, minio, two LLM SDKs, web-smtp,
webpush, cron) fails this repo's dependency principles.

**Bundling the sidecar in the default deploy.** Three processes, two identities,
two consoles, and a version-pinned engine shared across two projects.

**A provider registry now.** Two providers (local, notify) justify one interface,
not a registration system. The repo's own rule is to generalize on the third
concrete case.

## What would change the decision

- notify exposes an importable core with a constructor, a handler and a stop
  function, instead of a `main`.
- DagNats documents a supported version range for the bridge, and the bridge
  gains per-tenant credentials, making a shared engine supportable.
- A third delivery provider makes a channel registry cheaper than a switch.

## Open questions for upstream

1. Is there a roadmap for an embeddable core, or is the server the product?
2. Which DagNats versions does the bridge support, as a range rather than a pin?
3. Would a "notify as transport next to an app that already runs DagNats"
   quickstart be worth documenting on the notify side?

## Where this leaves the claim

A fresh clone must boot and work with zero external configuration; that is the
invariant, and it is why the landing page now says "nothing to operate" instead
of "zero external services". Providers are opt-in, never a boot requirement.
