# Supply-chain scanning: SBOM and image CVEs (2026-10-24)

Reviewed: 2026-10-24

The question: should gogogo generate an SBOM and scan its image in CI, and
with which tools? The answer chooses **Syft + Grype** as a separate,
SBOM-first workflow, not a runtime dependency and not a scanner wired into
the app. This note records the comparison and the parts that are easy to get
wrong in 2026.

## What each option is good at

| Tool | Shape | Strength | Cost |
|---|---|---|---|
| **Syft + Grype** | two pinned binaries: SBOM generator + matcher | SBOM is a first-class artifact; rescan the same inventory when the vulnerability DB moves; Grype adds EPSS/KEV/risk and refuses a stale DB | two tools to pin and update |
| **Trivy** | one binary: image, filesystem, IaC, secrets, SBOM | one CLI for everything; generates CycloneDX/SPDX itself | larger surface; its image default also runs secret scanning; March 2026 compromise of a release and force-pushed Action tags means SHA pinning is mandatory |
| **Docker Scout** | Docker-native, paid tiers | zero setup when everything is Docker | vendor lock-in and a dashboard outside the repo; less useful for an OCI image pulled by digest on a small box |
| **OSV-Scanner** | source/lockfile first | excellent for Go modules and PR checks; expiring ignores | image coverage is younger; not a replacement for an image SBOM |

The 2026 comparisons converge on a boring conclusion: on the same image,
Trivy, Grype and OSV-Scanner disagree by a few IDs, and an SBOM generated by
one tool can lose rows when read by another. A green scan is a statement
about inventory + matcher + database + policy, not a proof of safety.

## Why Syft + Grype for gogogo

- **The SBOM is the artifact.** Build once, store the CycloneDX file, rescan
  it later without pulling the image. That matches a repo that already pins
  artifacts by digest and keeps generated files reviewable.
- **No runtime dependency.** The app does not import a scanner; nothing new
  ships in the binary or the scratch image.
- **Grype's prioritisation is useful on a small team:** EPSS, CISA KEV and
  `--only-fixed` turn a wall of CVEs into "fix these now" instead of "ignore
  the scanner".
- **It complements, not duplicates, `govulncheck`:** `govulncheck` answers
  "is a known Go vulnerability reachable from my code"; the SBOM/image scan
  answers "what is actually in the image, including the base and the native
  libraries".

## What the workflow should do (separate PR)

1. After the existing image build, generate a CycloneDX SBOM from the built
   **digest** with Syft (`anchore/sbom-action`, pinned by full commit SHA).
2. Scan that SBOM with Grype (`anchore/scan-action`, pinned by SHA):
   `only-fixed: true`, `severity-cutoff: high`, fail the job on findings.
3. Upload SARIF to GitHub code scanning and keep the SBOM as a release
   artifact/attestation.
4. Run on `master`/release and on a schedule; do not rebuild an image on every
   docs PR just to scan it. A lockfile/Dockerfile change can trigger it.
5. Pin action SHAs and tool versions. The March 2026 Trivy incident is the
   concrete reason: a mutable tag is a supply-chain input, and a scanner is
   part of the supply chain it is supposed to protect.

## What not to do

- Do not gate on every CRITICAL. A base image with an unfixed CVE would block
  every deploy and train people to bypass the gate.
- Do not compare raw finding counts between scanners. Fold IDs to CVEs.
- Do not trust a green result on an end-of-life base image; check EOL
  explicitly.
- Do not wire a scanner into the app process. It is CI evidence, not runtime
  behaviour.
